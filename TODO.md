# ALAN.AI integrated project checklist

All items begin open. Mark an item complete only when its outcome has evidence; preserve the criteria when updating status. Keep this file current as implementation proceeds.

## 1. Public landing page and visual system — [ ]
- Build a professional, responsive ALAN.AI public landing page with a strong headline and clear call to action; overview academic-management and career-development features; explain timetable/attendance, announcements/calendar, opportunities, roadmaps and responsible AI assistance; concisely explain student, faculty and administrator experiences; provide login and registration links; and include a footer with relevant navigation and contact information.
- Use a cohesive, student-focused SaaS design with a restrained consistent palette, clear typography and hierarchy, comfortable spacing, rounded cards, subtle borders/shadows where appropriate, consistent iconography, accessible contrast, lightweight motion, skeleton loading states, helpful empty/error states, and consistent buttons, forms, dialogs, tables and navigation. Avoid excessive gradients, distracting motion, clutter, oversized decoration and generic disconnected dashboard templates.
- Desktop shell: collapsible left sidebar, distinctive ALAN.AI branding, academic and career/learning navigation grouped by purpose, top bar, contextual page title/actions, notification access, user profile menu, main content and useful breadcrumbs.
- Mobile: compact navigation; responsive cards/tables; mobile-friendly timetable/calendar; touch-sized targets; responsive forms/dialogs; no ordinary-screen horizontal overflow; prioritize frequently used student features.

## 2. Authentication, profiles, roles and access control — [ ]
- Use Supabase Auth. Implement student registration if enabled, login, logout, password reset, email verification where configured, persistent sessions, protected routes, loading/error states, profile creation/update and role-based dashboard redirection.
- Support student, faculty and administrator roles. Students can access only their own academic profile, timetable, attendance, announcements, academic events and authorized notifications. Faculty can access assigned classes, authorized student information, attendance workflows and permitted announcement-management features. Administrators can manage academic structure, users, timetable entries, academic events, announcements, attendance corrections and other authorized administrative operations.
- Never trust a client-supplied role; users cannot promote themselves to faculty/admin; protect role changes through trusted server-side operations; enforce authorization in both database policies and backend operations; validate access on every sensitive operation; do not expose private student information through public queries; use secure framework-supported session handling.
- Provide an administrator-controlled faculty/admin provisioning process; do not create a publicly accessible administrator-registration route. Never expose Supabase service-role keys, database secrets or other privileged credentials to client-side code.

## 3. Personalized dashboards — [ ]
- Student dashboard shows preferred name, current date and relevant academic context; summary cards for classes today, next upcoming class, overall attendance, unread announcements and upcoming academic deadlines; today’s classes in chronological order with subject, start/end time, classroom/lab, faculty if available and current/upcoming status; overall and subject attendance, below-threshold subjects and detailed attendance link; recent announcements with title, short description, publishing authority, publication date, priority and read/unread state; upcoming examinations, assignments, events and deadlines; and quick links to timetable, attendance, announcements, calendar and profile.
- All dashboard figures come from actual application data, never hardcoded production statistics. When data is absent, show helpful onboarding guidance and meaningful empty states.
- Faculty dashboard displays authorized assigned-class information. Administrator dashboard supports authorized academic management. Dashboard data must remain consistent with underlying records.

## 4. Student information and academic administration — [ ]
- Student profiles support full name, college email, optional configured profile image, department, degree/program, academic year, semester, section, optional college-required student identifier and account status; collect only necessary information.
- Provide administrative support for departments, programs, academic years, semesters, sections, subjects/courses, faculty assignments, student course enrollments, classrooms and timetable assignments.
- Use structured relationships rather than free-text department/subject names where appropriate; maintain referential integrity with foreign keys, uniqueness constraints and validation.

## 5. Timetable and class-session management — [ ]
- Students can view daily and weekly timetables; navigate days/weeks; view subject details, class time, room, faculty and session status; identify free periods; highlight the next class; see timetable changes/cancellations; and filter by relevant academic period when appropriate.
- Faculty can view assigned classes by date/week, access relevant class information and see associated students only when authorized.
- Administrators can create/edit/deactivate/delete incorrect timetable entries; assign subjects, faculty, rooms, sections and time slots; validate conflicting room/faculty assignments; configure semester/academic-year data; and support timetable changes and cancelled sessions.
- Store recurring timetable definitions separately from actual dated class sessions so attendance, cancellations, substitutions and changes are represented correctly. Validate time ranges and prevent unintended conflicts. Store timestamps consistently and display them in the college-configured time zone.

## 6. Academic calendar and events — [ ]
- Support internal examinations, semester examinations, assignment deadlines, project reviews, laboratory sessions, seminars/workshops, college holidays, department events and other academic activities.
- Provide monthly and weekly calendars, an upcoming-events list, event details, categories/labels, start/end dates, optional location/description, department/semester/section targeting, authorized event create/edit workflows and past-event handling. Validate date ranges.
- Administrators can publish college-wide and targeted events. Distinguish event categories clearly without overwhelming the calendar.

## 7. Announcements — [ ]
- Students can view relevant announcements, search, filter by category/priority, open full details, see publication/expiry dates, mark as read, access authorized attachments and distinguish urgent notices from ordinary updates.
- Faculty can create/manage announcements only when permitted. Administrators can create/edit; publish/unpublish; schedule publication when supported; set priority and expiry; target departments, semesters, sections or the entire college; manage attachments; and review previously published notices.
- Keep drafts distinct from published notices; prevent students from modifying official announcements or accessing notices intended exclusively for other groups; maintain publication/modification metadata; report a notice as published only after the database operation succeeds.

## 8. Student attendance views and calculations — [ ]
- Use one consistent formula across dashboards, reports and detail pages: attendance percentage = (number of counted attended sessions / number of counted conducted sessions) × 100. Explicitly define counting rules; cancelled classes do not automatically count as conducted; excused absences and exceptional cases follow configurable policy rather than inconsistent silent behavior.
- Students can view overall and subject-wise attendance, attended/conducted counts, historical records, subject/date filters, below-threshold subjects and the calculation explanation. Show an estimate of additional classes needed to reach a target when mathematically possible. Clearly label estimates and never imply future eligibility is guaranteed. Show a meaningful state for zero conducted classes.
- Students may submit correction requests only if that workflow is implemented; they must never directly modify their own official attendance.

## 9. Faculty/admin attendance workflows and integrity — [ ]
- Faculty can select an assigned class session; view its enrolled students; mark present/absent; review before submission; submit; view submitted records; correct only when authorized; and provide a correction reason when policy requires it.
- Administrators can review records; authorize permitted corrections; inspect summaries; manage thresholds/policies; review correction history; and generate class-wise/subject-wise reports.
- Every attendance record belongs to one student and one dated class session; prevent duplicate student/session records; verify faculty assignment before accepting submissions; use transactions or an appropriate atomic database operation for bulk entry; prevent unauthorized modification of submitted records; record creators/modifiers; audit sensitive corrections; and recalculate summaries from authoritative records.

## 10. In-app notifications — [ ]
- Provide user-specific notification lists, read/unread indicators, mark-as-read actions and links to the relevant application page. Notifications may be created for important announcements, timetable changes, upcoming examinations, assignment deadlines and other important academic events.
- Avoid duplicate notifications if an event is updated or processed more than once. Email/browser-push/other channels are optional; in-app notifications are required.

## 11. Database, migrations, seed data and RLS — [ ]
- Provide a normalized, documented schema and version-controlled migrations. Include equivalent structures for `profiles`, `departments`, `programs`, `academic_years`, `semesters`, `sections`, `courses`, `course_enrollments`, `faculty_assignments`, `timetable_entries`, `class_sessions`, `attendance_records`, optional `attendance_correction_requests`, auditable `attendance_audit_logs`, `announcements`, `announcement_targets`, `announcement_reads`, `academic_events` and `notifications`; add storage metadata if attachments are supported, audit records for sensitive admin changes, and attendance-policy/college settings where needed.
- Use consistent UUIDs/identifiers; foreign keys; uniqueness constraints for duplicate-sensitive data; indexes for common queries; deliberate delete behavior; timestamps and created/updated metadata where appropriate; and avoid unnecessary sensitive information. Explain important relationships. Do not substitute hardcoded frontend arrays for database-backed functionality.
- Enable RLS for all tables exposed to application clients and implement/test policies: students only see their private profile/attendance and targeted notices; faculty only assigned classes/permitted records; admins perform authorized operations; attendance submissions verify assignment; users cannot edit their own role through ordinary profile updates; attachments (if any) are private to authorized users. Use trusted server code/database functions for privileged validation; hiding UI controls is not authorization; never expose service-role credentials to browsers.
- Provide a safe, repeatable, clearly development-only seed process with synthetic records for several departments/courses/sections, faculty/students, timetables, upcoming events, published announcements and attendance. Store no real student data, credentials or private information in source. Document test-account creation and manual provisioning of privileged accounts.

## 12. Phase 2 career opportunities and discovery — [ ]
- Build an authenticated student opportunity portal with search and type/work-mode filters, details, save/unsave bookmarks and a personal application tracker. Prevent duplicate applications with a database uniqueness rule; allow the student to update status and notes; keep every record private to its owner.
- Provide a college-admin workflow to create and manage listings with title, company, type, domain, location, work mode, skills, description, deadline, source URL, provenance, verification status and publication status. Students may see only published, verified opportunities with a source; supplied example.com job rows remain unpublished and clearly unavailable as live opportunities.
- Persist career discovery interests, learning style, available time, skills and target domain for the authenticated profile. Explain the recommendation method; recommendations are a transparent heuristic, not an AI fit score; allow comparison of suggested career paths without claiming unverified salary/outcome data.

## 13. Phase 2 roadmaps, resources and assessments — [ ]
- Support personalized roadmaps with title, domain, weekly hours, status, ordered milestones, phases and descriptions; persist plans/tasks in Supabase; calculate progress from saved task completion; let the student toggle completion and record task notes; clearly identify AI-generated plans and provide a transparent unavailable/error state if generation is not configured.
- Support AI-assisted roadmap generation from a validated career goal, skill baseline and available weekly hours; bound requested/output length, validate the structured result, save it under the signed-in student, never invent provider-backed resources or promise outcomes, and retain a clearly labelled starter alternative only when shown as non-AI.
- Provide a curated resource library with search, difficulty filter, resource detail/provider/source links and user-specific persistent bookmarks; identify resources as curated starting points and do not claim availability was checked when it was not.
- Provide objective assessments that deliver questions/options without exposing correct answers before submission; score on the server/database, persist attempt history per student, and reveal score, correct answer, and explanation only in that student's saved result after submission.

## 14. Phase 2 mock interviews and AI companion — [ ]
- Provide private student-owned mock-interview sessions with target role, interview prompts, persisted answers, continuation/history, and transparent coaching feedback. If feedback uses the supplied deterministic rubric, label it as reflection guidance and never as AI evaluation, grading or a verified score.
- Provide a private, persistent AI companion conversation list/history, create/select/delete conversation actions, bounded message input/output, per-user persistent short-term request limiting, timeout handling, safe validation, useful unavailable/provider-error states and clear distinction between study help and career guidance. Staff/admin must not have access to private chat or interview content by default.
- Call only a server-side OpenAI-compatible provider. Use the three protected `ALAN_AI_API_KEY_1`, `ALAN_AI_API_KEY_2` and `ALAN_AI_API_KEY_3` values in sequential fallback rotation; keep keys out of browser bundles, source, Git, logs and examples; allow a server-only configurable HTTPS base/model; rotate only through bounded requests and do not claim the provider/key combination works until verified. Include profile/career context only when a student explicitly enables sharing, and send only the minimum needed context.

## 15. Integrated architecture, data security and application states — [ ]
- Integrate the supplied Phase 2 package into the existing Next.js/Supabase application, sharing the Phase 1 Supabase Auth, profile identity, session, responsive shell, design primitives, validation conventions and server-side authorization. Do not ship the standalone demo HMAC login, demo-user autofill, SQLite persistence, Express/Vite runtime or duplicate product shell.
- Organize maintainable academic and career feature modules, shared components/validation/types, route handlers/server actions, Supabase migrations and tests. Keep business logic out of large UI components; all required user-specific feature state persists in Supabase. Keep Phase 2 tables prefixed/namespaced consistently and map every owner FK to the Phase 1 auth/profile model.
- Enable RLS for every client-accessible career table. Students can read/change only their own profile/preferences, bookmarks/applications/roadmaps/tasks/attempts/interviews/conversations/messages; published verified opportunities and published learning resources are visible to students; administrative listing changes require server/database-enforced administrator authority; interview/chat content is not accessible to staff; assessment answer keys are never client-readable; rate-limit data is not directly client-writable. Never trust a client-supplied user ID or role.
- Keep academic and career features modular but unified in ALAN.AI. Handle loading, skeleton, empty, validation, success, missing-configuration and error states throughout. No fake production job data; do not silently claim AI service or live opportunities work when external configuration is unavailable.
- Handle appropriate loading, skeleton, empty, validation, success and error states throughout. Missing service configuration must produce a useful message, never silently fall back to fake data.

## 16. Automated tests, accessibility, performance and release checks — [ ]
- Create and execute critical automated tests, inspect failures and fix genuine issues. Cover auth login/logout/protected routes/session/password reset where testable; authorization for cross-student access, role changes and admin actions; timetable valid/invalid times/conflicts/cancellations/display; attendance calculations/zero classes/duplicates/bulk/cancellations/corrections/unauthorized changes; announcement audience/draft-versus-published/expiry; event date validation; read state; opportunity visibility/unique applications/status updates; own-record career profile/bookmark/roadmap/interview/chat isolation; task completion; assessment answer-key isolation/scoring/history; companion validation/rate-limit/key-fallback/error states; and UI responsive navigation/forms/loading/empty/error plus student/faculty/admin workflows.
- Use server-side data fetching where appropriate; pagination for large lists; indexes for common filters; avoid repeated queries; lazy-load nonessential content; use optimistic updates only with failure handling. Provide keyboard access, visible focus, accessible labels, semantic structure, appropriate contrast and screen-reader support. Do not sacrifice security or data integrity for performance.
- Verify modules integrate, dashboard data matches authoritative records and production build succeeds. Run type checks, lint, tests and migration/policy checks; accurately report every verified/unverified result. Do not claim success for untested features or unresolved critical security issues.

## 17. Environment, setup, deployment and handoff — [ ]
- Provide an environment-variable template with no secrets; local-development, Supabase project setup, migrations, seed, build/test and production deployment instructions; explain required third-party services. Never commit actual secrets. Keep service-role/provider/database secrets server-only. Keep the three AI credentials in protected runtime settings only; document the configurable HTTPS OpenAI-compatible base/model as names/placeholders without secret values.
- Make the application deployable. If deployment credentials are unavailable, complete and verify what can be done locally and document the remaining steps; do not claim deployment succeeded unless confirmed. Keep repository changes under Git/version control and provide complete source code.
- Push the integrated ALAN.AI source, documentation, migrations and lockfile to the user's requested GitHub repository without committing secrets, generated build output, `.env` files or the standalone demo ZIP as executable source. Preserve the existing repository history, inspect diffs, scan tracked files for credential leakage and require the push to `main` to succeed before saying the requested push is complete.
- Final handoff lists completed features, known limitations/unresolved issues, tests and build results, database migrations/schema, RLS/authorization documentation, safe synthetic data, environment template, setup/deployment guide and the GitHub push result. The final report states what was built, what could not be verified, and external configuration/migration steps still required.
